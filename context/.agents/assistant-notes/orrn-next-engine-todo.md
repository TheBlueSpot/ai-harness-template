## External Sources

- Source facts:
  - Phaser installs through npm or a create-game CLI and leans on a starter flow that gets a project running quickly.
  - PixiJS centers a modern `Application` init flow, async setup, typed options extension, and a docs split between getting started, API reference, and examples.
  - Three.js keeps install/import explicit, uses `three` plus separate addons subpaths, and documents renderer/camera/setup in a small manual-first path.
  - p5.js keeps the learning path beginner-shaped, with `setup()` and `draw()` as the core loop and a heavy tutorial/reference split.
  - Rapier's JS docs make async WASM loading explicit, offer a compat bundle when bundlers are weak, and expose deterministic simulation plus debug and serialization surfaces.
  - Bevy's public README emphasizes modularity, examples, fast compiles, and early API churn, with web examples and wasm-bindgen-based web output in the repo.
- Inference:
  - The engine should keep install/import shape explicit, separate core deterministic primitives from browser-only convenience, and make typed init and asset-loading boundaries first-class DX.
  - The best comparable pattern for `./engine` is "small core, explicit subpaths, async or caller-owned asset setup, and docs that separate quick start from API boundaries."
  - Browser-facing fallback should stay quiet by default, but setup failures need opt-in diagnostics when WASM delivery is involved.
  - Helper growth should stay tied to real consumer jobs, not source-layout adjacency.
