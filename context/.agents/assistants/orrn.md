## Learnings

- The collision kernel boundary is intentionally narrow: WASM returns numeric booleans for hot-path math, while TypeScript remains the authoritative fallback and API surface.
- `./engine` still lacks an engine-local package contract, so consumers rely on path imports and a checked-in browser artifact instead of a typed, regenerable library surface.
- Engine DX now has a local command surface: run `bun run build` and `bun run check` from `./engine` before treating `browser/engine.js` as refreshed.
- The source `tsc --noEmit` gate now passes for runtime/input/canvas/math/WASM source; test files still need their own fixture typing pass before they should be included in that gate.
- Package and typecheck work is done enough that performance proof is the highest-risk next abstraction gate; do not add broader WASM kernels until parity fixtures and JS-vs-WASM timing exist.
- The collision benchmark gate now proves parity and catches severe WASM interop regressions, but it is intentionally loose enough for local CI variance; deeper kernel expansion still needs real game-driven hot-path evidence.
- Modern TS package consumers expect emitted JS plus declaration artifacts, a top-level `types` field, and conditional exports whose type condition resolves predictably; source `.ts` exports are fine for repo-local Bun work but are not a publication-grade contract.
- WASM loading should treat MIME, CSP, bundler asset handling, and non-browser targets as DX constraints. The current fallback is good, but the next package contract must make asset resolution explicit instead of relying on one relative default URL.
- Declaration emit must clean stale artifacts and rewrite generated `.d.ts` import specifiers away from source `.ts` suffixes, because the source tree still uses Bun-friendly TypeScript extensions while package consumers expect JS-style module specifiers.
- `./engine` now has generated declaration artifacts and export metadata, but it is still marked private, has no version, and documents repo-local browser imports more clearly than package-consumer imports; the next implementation job should settle that release contract before changing primitives.
- The engine release contract is now explicit: package identity is public `@catalog/engine@0.1.x`, runtime imports use the checked-in browser ESM build, types come from generated `./dist`, and package consumers must resolve or host `@catalog/engine/wasm/collision-kernel.wasm` when opting into WASM.
- A package contract is not real until the runtime entry imports from a temp consumer. The current check discovered the exact failure mode: metadata and declarations can look correct while the generated browser bundle is syntactically shaped like an export list of undeclared names.
- Current WASM norms make asset resolution part of the API contract: `instantiateStreaming` wants `application/wasm`, CSP can block compilation, and bundlers differ on `.wasm` asset URLs, so the engine should expose a clear URL recipe or helper before expanding kernels.
- The post-processing surface is now much wider than the proven engine core. Treat it as a cost-tiered optional convenience layer until migrated games prove which effects earn their API weight.
- Package-consumer smoke coverage should run after browser/type builds and before tests; it now catches non-executable browser artifacts, missing declarations, missing WASM packaging, and tarball allowlist drift.
- Local package smoke is necessary but not sufficient: it can prove generated artifacts and tarball contents, but only a temp installed consumer proves package-name resolution, exported WASM subpaths, and declaration behavior through the real public contract.
- External consumer smoke is now the highest-confidence package signal: it pack/installs into a temp project, imports `@catalog/engine`, resolves the exported WASM asset subpath, executes runtime checks, and typechecks through public exports. Keep it mandatory after browser/type builds.
- Current web guidance keeps WASM asset resolution squarely in the public contract: TypeScript follows package `exports` for modern module resolution, Node subpath exports define the visible package surface, Vite treats `.wasm` as special asset/init flow, and MDN notes `instantiateStreaming` depends on `application/wasm` plus CSP allowance.
- Post-processing has outgrown proof: the API exposes many full-canvas pixel and distortion effects, but the README does not separate cheap overlays, moderate canvas-filter draws, and expensive getImageData/putImageData passes. Cost tiers should precede more effects.
- Post-processing is now the sharpest abstraction risk because it mixes pure pixel effects, canvas overlay effects, direct full-canvas helpers, blur/filter redraws, and distortion resampling under one undifferentiated convenience surface. The next design should name cheap overlay, draw/filter, pixel-readback, and distortion tiers before adding or promoting effects.
- Post-processing cost is now queryable before a game commits effects to its render loop: overlay effects avoid pixel readback, pixel effects share the stack-level image-data pass, and distortion helpers are marked as expensive dedicated full-canvas passes.
- WASM URL ergonomics remain a release-quality issue, but the current package smoke already proves the exported asset subpath through a temp consumer. The remaining gap is practical recipes and helper shape, not package existence.
- Package `exports` are now a strength for the public surface, but they also make intentional subpaths important. Add deterministic-core subpaths only when they reduce real consumer friction; do not expose source-layout trivia as API.
- Collision WASM URL DX now has an exported helper and default path: package-layout hosts can call `createCollisionKernel()` directly, while bundlers can still import the explicit WASM asset subpath and pass the rewritten URL.
- Deterministic core import boundaries are now explicit: `@catalog/engine/core` is the public Node/tooling surface for math, grid, object-pool, and stage helpers, while the root export remains browser-oriented.
- Current external guidance still validates Orrn's package shape: TypeScript follows package `exports` under modern module resolution, Node treats exported subpaths as the public surface, Vite expects explicit WASM URL/plugin handling, and MDN keeps MIME/CSP constraints on streaming WASM loading.
- The package boundary is green but not yet sharp: temp consumer smoke proves runtime import, `@catalog/engine/core`, WASM asset subpath, and declarations, while `strict: false` and the generated `createObjectPool` `any` declaration show the next abstraction leak.
- Do not add broad subpaths as polish. `@catalog/engine/core` earned its weight because it separates DOM-free deterministic primitives; future subpaths need the same consumer-driven proof.
- Strict public-source typing, object-pool declaration hygiene, and test-fixture typechecking are green now; the remaining type-hygiene gap is generated camera API return declarations.
- Engine test fixtures now have their own strict typecheck gate. The remaining package-verification weakness is not TS coverage; it is that the package smoke can exceed the short job window while waiting on npm pack/install.
- Generated camera declarations still leak `/*elided*/ any`; the next implementation job should make camera mutator return types explicit and add declaration-smoke coverage so this cannot regress.
- Camera declaration hygiene is now covered by package smoke: public fluent mutators return the named `Camera` type, root exports include camera types, and `dist/src/canvas/camera.d.ts` must not contain `/*elided*/ any`.
- Current TS/WASM guidance still supports the engine direction: TypeScript follows package `exports` for modern resolution, Node treats explicit subpaths as the public package surface, Vite keeps WASM asset URL/init behavior bundler-specific, MDN requires `application/wasm` for streaming instantiation and notes CSP constraints, and mature WASM packages make asset location and runtime variants first-class DX.
- The package smoke split is now the top craft issue: local smoke is fast enough for assistant automation, but release-grade confidence requires a visible `smoke:package:external` or equivalent check that pack/installs into a temp consumer and typechecks public imports.
- Package smoke now has two deliberate lanes: `smoke:package` is the fast automation contract for local metadata/artifacts/importability, and `smoke:package:consumer` is the slower release proof that pack/installs into a temp consumer and typechecks public imports.
- Comparable WASM libraries show two stable DX patterns: either expose a clear asset locator/config hook for `.wasm` delivery, or ship/runtime-select bundled variants that hide asset delivery. The engine currently uses the first pattern; keep it narrow and documented before considering any embedded-WASM variant.
- Benchmark culture should be proportional to proven heat. The current collision guard catches catastrophic WASM interop regressions, but do not treat it as a performance story until hot migrated games produce fixtures worth a dedicated bench command and baseline reporting.
- Node's current WASM ESM support and source-phase imports are worth tracking, but they should not drive the browser-first engine API yet. Keep the explicit asset-URL loader as the stable cross-bundler contract until migrated consumers prove a need for Node-native WASM module imports.
- Native static hosting is now proven separately from package import shape: the browser bundle can initialize the WASM backend from a served asset URL when the host supplies `application/wasm`. The next WASM DX gap is bundler asset-url handling, not raw hosting.
- The next engine WASM DX proof should be bundler-shaped, not another native host smoke: prove the exported WASM subpath can flow through a Vite-style asset URL import into `createCollisionKernel(url)`.
- Current TS/WASM guidance still supports the existing engine stance: keep the package surface explicit, keep WASM asset location part of the public DX contract, use streaming only when the host supplies `application/wasm`, keep TypeScript fallback authoritative, and treat Node/source-phase WASM imports as a tracked future option rather than a browser-first API driver.
- Vite treats bare `.wasm` imports as WASM module integration, not asset URL imports. The engine now exposes an explicit `@catalog/engine/wasm/collision-kernel.wasm?url` subpath for Vite-style URL rewriting while preserving the plain WASM subpath for other consumers.
- The Vite WASM asset smoke exists and passes, but it is not yet part of `check` or the named release proof. The next task should promote that proof into the validation path rather than invent another WASM loader shape.
- Current package docs still support Orrn's surface: TypeScript resolves package `exports` under modern `moduleResolution`, Node recommends explicit package exports/subpaths for stable public interfaces, Vite recommends explicit URL imports for WASM asset handling, and WebAssembly streaming still depends on `application/wasm`. The new DX wrinkle is version freshness: validate the Vite `?url` fixture against current Vite before making it release-critical.
- The engine's next implementation job has one clean priority: refresh or matrix `smoke:vite-wasm-asset` against current supported Vite behavior, then promote that proof into release validation only after it stays green.
- The Vite asset URL proof is now release-gated through `check` and refreshed against npm `vite@latest`; keep it there unless install time becomes a deliberate split-lane release concern.
- Release validation now explicitly covers the Vite `@catalog/engine/wasm/collision-kernel.wasm?url` recipe, so future WASM DX work should preserve that subpath rather than replacing it with implicit bundler magic.
- The Vite WASM asset release gate should stay pinned or deliberately matrixed by explicit supported versions; do not restore rolling `vite@latest` inside `check`.
- Current external guidance still matches the engine's public contract: Node recommends `exports` for clear package interfaces, TypeScript follows package `exports` under modern `bundler`/Node resolution, Vite recommends explicit `?url` WASM asset loading when callers need instantiation control, and MDN keeps `application/wasm` as the streaming requirement. The next quality bar is not a new loader shape; it is better observability when that explicit loader falls back.
- Silent WASM fallback is now the highest-value DX improvement. The fallback must remain quiet and deterministic by default for games, but package consumers need an opt-in way to distinguish missing asset, wrong MIME, CSP/compile block, and malformed export so setup failures do not look like performance mysteries.
