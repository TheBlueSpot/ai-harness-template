# Durable Learnings

- Shared playtest capture should carry one cross-lens incident queue for this catalog, because repeated browser-play breakage is easier to prioritize when recurrence, impact, persistence, and player cost travel with the same tag into every downstream audit.
- Shared playtest capture should log early-loop cadence for this catalog, because simple browser-playable games can look clean in later audits while still losing stickiness if first agency or first payoff lands too late to reinforce the core verb.
- Shared evidence capture matters for this catalog because one browser-play session often feeds several audit lenses; logging scope and raw observations once reduces cross-skill drift and makes repeated game analysis more comparable.
- Coverage gates matter because thin samples can look persuasive in prose; the skill should mark which downstream audit lenses are actually evidence-ready and which still need a busy frame, fail-retry, beat timeline, or contact sample.
- Shared evidence capture plus explicit coverage gates matter for this catalog because one browser-play session often feeds several audit lenses; logging scope, sampled contexts, and raw observations once keeps downstream claims tied to what was actually seen instead of persuasive but thin prose.
- Shared evidence capture needs explicit claim ceilings for this catalog because one short browser-play session can feed many audits; logging sampled contexts, missing contexts, and what later reviewers still may not claim keeps thin evidence from hardening into confident catalog lore.
- Shared evidence capture should include at least one interruption-resume probe for this catalog because sticky arcade judgment falls apart when first-run notes ignore whether players can recover the current goal, controls, and next action after a short break or tab switch.
- Shared evidence capture should log input certainty and view support for this catalog because sticky browser-game audits go off-course when HUD, pacing, or failure notes blame readability alone for deaths actually caused by camera obstruction, auto-camera drift, or unstable response.
- Shared evidence capture should also log chain-punish deaths and retry-lesson stability for this catalog because failure-loop judgments go wrong when fast restart hides the fact that one mistake still snowballs or that retry does not reproduce the same teachable problem.
- Shared evidence capture should log cue-competition moments and mechanic-stack readability for this catalog because sticky arcade failures often come from unreadable overlap, and downstream HUD or pacing audits should not have to reconstruct that overlap from memory.
- Shared evidence capture should log cue-competition moments and mechanic-stack readability for this catalog because sticky arcade failures often come from unreadable overlap, not from one isolated HUD or pacing problem.
- Shared evidence capture should log temporary prompt recovery for this catalog because sticky browser-game reads fail when critical cues disappear before they can be rechecked and when non-critical popups cannot get out of the way.
- Shared evidence capture should track retries separately from failures for this catalog because a death count alone cannot prove that restart friction, return-to-lesson speed, or retry stability were actually observed.
- Session-derived durable learning matters for this catalog because the strongest reusable playtest insight should mirror into repo-local Kojima memory with the starter files instead of living as one fixed repeated line.
- Shared playtest capture should save fail-retry evidence into repo-local Kojima memory, because restart speed alone does not show whether death reads clearly or whether the same lesson survives the retry.
- When players praise a tiny arcade game's feel but say it ends too fast, first add named stages and route-remixed enemy waves around the same verb; light campaign framing and readable variation usually deepen stickiness better than bolted-on systems.
- Shared playtest capture should start from a reusable probe deck in this catalog, because task-based first-contact, busy-frame, fail-retry, resume, and contact prompts cut evaluator drift better than open-ended `play for a bit` sessions.
- Shared playtest capture should log cue-channel fallback for this catalog, because color-only or audio-only warnings can look readable in one short browser-play session while still failing real players under mute, color ambiguity, or screen-noise conditions.
- Shared playtest capture should score each probe with task success plus confidence, satisfaction, and frustration, because a browser-game beat can technically complete while still feeling untrustworthy or costly enough to mislead downstream onboarding, HUD, pacing, or failure-loop judgments.
- Shared playtest capture should save repeated incident tags into repo-local Kojima memory, because repeat count plus impact shows which browser-play failure keeps resurfacing across onboarding, HUD, pacing, or failure reviews.
- Shared playtest capture should emit a dedicated settings-and-assists starter with recovery-trust fields, because live or post-failure reachability, progress-safe changes, reminder or practice recovery, and retry persistence otherwise get re-entered by hand and drift away from the shared observation packet.
- Shared playtest capture should save lightweight probe workload into repo-local Kojima memory, because a browser-game beat can technically succeed while still feeling too mentally loaded or rushed to support sticky play.

- Shared playtest capture should add a browser responsiveness probe to repo-local Kojima memory, because first input, restart readiness, event timing, and long-animation-frame blocking each need explicit fallback reasons when the browser does not expose the full observer surface.
- Shared playtest capture should route responsiveness questions through the dedicated probe lane first, because FPS-only notes hide whether input or restart actually answered fast enough for trust.
- Shared playtest capture should reuse control-ready gap evidence for later activation and trust audits, because one timing sample is more durable than restating the same lag as a vague smoothness complaint.
- Shared playtest capture should add a readable-progression lane for this catalog, because proximal goals, prerequisite progress, evaluative readback, and non-comparative next-step guidance need their own starter and guardrail shape.
- The telegraph-versus-responsiveness split should stay explicit in this catalog, because telegraph readability already has shared evidence fields and neighboring audits while responsiveness had a shipped probe with a concrete timing defect that could be fixed immediately.
- Browser responsiveness output should label `event-timing`, `requestAnimationFrame` estimate, and unsupported observer surfaces separately, because `felt fine` is weaker than saying exactly which timing source was real, estimated, or missing.
- Browser responsiveness output should preserve derived `inputDelay`, `handlerDuration`, and `presentationDelay` in each `PerformanceEventTiming` sample, because later trust reviews need to know whether latency lived before handler work, inside it, or before paint.
- Restart evidence should separate `restart-to-next-paint` from `restart-to-control-ready` in this catalog, because a visible restart response can still precede the first moment the next probe input actually gets a painted answer.
- Shared playtest capture should also save one trace-backed evidence pack for this catalog, because a Playwright trace plus targeted screenshots lets later boot, restart, and cue-overlap audits inspect the exact failure state without replaying the whole run.
- Shared playtest capture should add a forgiveness lane for this catalog, because coyote time, input buffering, corner correction, collision leniency, and `stolen fail` evidence otherwise get re-logged by hand even though they belong in the same sampled session.
